# مواصفات تحويل Sanky POS إلى منتج لمحلات متعددة

**الحالة:** المتطلبات موثقة؛ تصميم قاعدة البيانات المشتركة لم يُنفذ بعد
**تاريخ التوثيق:** 2026-10-24
**حدود هذه الوثيقة:** تلخص قرارات المستخدم، وتوثق فجوات محلية شوهدت بقراءة محدودة للكود. لا تثبت حالة قواعد البيانات أو إعدادات Vercel الحية.

## 1. الهدف

تحويل البرنامج الحالي، الذي يخدم محل سانكي، إلى منتج يمكن لصاحبه تجهيز حسابات لمحلات أخرى وبيعها باشتراك شهري. تبقى بيانات كل محل منفصلة، ويحصل الموظفون على واجهة مشتركة مع إعدادات المحل وباقته.

## 2. القرارات المتفق عليها

### الحسابات والدخول

- بوابة دخول مشتركة واحدة للمحلات، ورابطها في البداية رابط Vercel مؤقت.
- لكل محل رقم تعريف فريد من 4 أرقام؛ يُدخل العميل رقم المحل ثم الإيميل وكلمة المرور.
- رقم المحل معرّف للمحل وليس كلمة مرور. 4 أرقام تتيح حتى 10,000 رقم؛ يلزم تمديدها إذا تجاوز عدد المحلات ذلك.
- صاحب المحل يستعيد كلمة مروره بنفسه عبر رابط على الإيميل. يستطيع مالك المنصة طلب إرسال رابط استعادة جديد من لوحة التحكم، من دون عرض كلمة المرور أو معرفتها.
- لوحة مالك المنصة تكون ضمن بوابة الإدارة المحمية، ولا تعرض مبيعات المحلات أو بيانات عملائها.
- لا يُشترط التحقق بخطوتين لحساب مالك المنصة حسب القرار الحالي. يلزم تسجيل عمليات الإدارة، وتحديد محاولات الدخول، واستخدام كلمة مرور قوية. يمكن إضافة MFA لاحقًا.

### إعداد المحلات والفروع

- مالك المنصة ينشئ حساب كل محل ويحدد باقته واشتراكه.
- كل محل جديد يبدأ ببيانات تشغيل فارغة تمامًا؛ لا تُنسخ إليه منتجات أو موظفون أو طلبات سانكي.
- أول دخول لمالك المحل يعرض معالج إعداد لإدخال اسم النشاط وشعاره وعملته وبيانات الضريبة والإيصال، ثم إنشاء الفرع الأول وإضافة الموظفين والمنتجات.
- ألوان البرنامج موحدة. اسم المحل وشعاره وإعداداته التجارية خاصة به.
- المحل الواحد قد يضم عدة فروع. المنيو والأسعار مشتركة بين الفروع افتراضيًا، مع السماح باستثناءات لفرع محدد.
- لا يستطيع العميل إنشاء فرع يتجاوز الحد المخصص له. عند بلوغ الحد تظهر رسالة تفيد بانتهاء عدد الفروع المتاح؛ يضيف مالك المنصة رخصة فرع ويصدر كودًا للعميل. تنطبق آلية الموافقة والرخصة على الأجهزة أيضًا.
- تفاصيل الاشتراك قابلة للتعديل لكل عميل بصورة مستقلة: مستوى الموديولات، عدد الفروع، عدد الأجهزة، السعر الشهري، وتاريخ الانتهاء. حدود الفروع والأجهزة ليست مفروضة آليًا بواسطة مستوى الموديولات.

### الباقات والميزات

| المستوى | المحتوى المتفق عليه |
| --- | --- |
| الأساسي | الكاشير، الطلبات، تقارير البيع والورديات الأساسية، والتوصيل |
| الثاني | محتوى الأساسي + HR + المخزون |
| الأعلى | محتوى الثاني + الولاء + Finance |

- الطاولات والطلبات المحلية إضافة اختيارية.
- التوصيل موجود مع الكاشير في كل الباقات. نوع الطلب يحفظ بيانات العميل والعنوان ورسوم التوصيل، ويظهر في تقارير حسب نوع الطلب.
- رسوم التوصيل قابلة للضبط من إعدادات المحل: قيمة ثابتة، حسب المنطقة، أو مفتوحة يحددها الكاشير لكل طلب.
- رسوم التوصيل تدخل في إجمالي المبيعات، وتظهر كذلك كسطر منفصل في الإيصال والتقرير. طريقة الدفع تظل كاش/فيزا/غيرها.
- يمكن للمحل إنشاء أنواع طلبات أخرى من الإعدادات وعرض تقاريرها.
- البيع عند نفاد المخزون إعداد على مستوى المحل. عند السماح بالبيع السالب، الكمية المتاحة وقت البيع تُحسب بتكلفتها، والزيادة فوق المتاح تسجل بتكلفة صفر حسب قرار المستخدم؛ يجب إظهار تنبيه لأن ذلك يرفع الربح الظاهر مقارنة بالتكلفة الفعلية.

### الاشتراك والإدارة

- الاشتراك شهري، والتحصيل يدوي. مالك المنصة يسجل استلام المبلغ ويجدد الاشتراك.
- مالك المنصة يحدد التجربة لكل محل يدويًا، من دون مدة تجربة ثابتة مفروضة.
- يظهر للعميل عدّاد مدة الاشتراك. ترسل رسائل بريد قبل الانتهاء بـ7 أيام و3 أيام ويوم واحد، ورسالة عند الانتهاء.
- بعد انتهاء الاشتراك يتوقف البيع الجديد فقط، وتظل البيانات والطلبات والتقارير متاحة للعرض والتصدير.
- إذا ظل الكمبيوتر بلا تحقق من الاشتراك، فمهلة العمل أوفلاين القصوى 3 أيام؛ بعدها يتوقف البيع الجديد حتى يعيد الاتصال والتحقق.
- عند إلغاء العميل، تعرض لوحة المالك خيار الاحتفاظ بنسخة من بيانات المحل لاستخدامها لاحقًا أو حذف بيانات المحل كلها. لا حذف تلقائي قبل الاختيار.

### برنامج الكمبيوتر والتزامن

- أول تشغيل لبرنامج الكمبيوتر يطلب كود تفعيل يصدره مالك المنصة. الكود صالح 24 ساعة ولمرة واحدة، ويرتبط بمحل وفرع وجهاز محددين.
- بعد التفعيل، يحمّل البرنامج بيانات التشغيل اللازمة للكاشير في ذلك الفرع. استخدام كود التفعيل لا يتكرر عند كل دخول.
- دخول الكاشير اليومي برقم PIN من 4 أرقام خاص بكل موظف.
- على شاشة PIN يوجد زر **مزامنة المستخدمين**. بعد تغيير PIN أو صلاحيات موظف، يسجل الكاشير خروجه ويضغط الزر قبل الدخول؛ يسحب بيانات الموظفين والصلاحيات والتحقق المحدث للفرع. لا تُطبق التغييرات تلقائيًا قبل هذا الإجراء.
- عند الاتصال، مزامنة المستخدمين تجلب أحدث حالة للموظفين وصلاحياتهم. عند الانقطاع، يمكن استخدام آخر بيانات مزامنة محفوظة حتى مهلة الأوفلاين القصوى المتفق عليها.
- يعرض برنامج الكمبيوتر وموقع الإدارة حالة الجهاز ووقت آخر مزامنة بجانب الجهاز.
- طلبات البيع المحفوظة أوفلاين تُرسل تلقائيًا عند عودة الاتصال مع منع تكرار الطلب.
- تغييرات الموقع على الأسعار أو الواجهة لا تصل إلى الكمبيوتر إلا بعد الضغط على مزامنة الكمبيوتر. إلى ذلك الحين يبيع الكمبيوتر بالأسعار التي كانت عند آخر مزامنة. كل طلب يحتفظ بسعره وخصمه وطريقة دفعه وقت البيع.
- بعد نشر تحديث جديد، يُختبر على محل تجريبي ثم يُعمم على العملاء. يشمل النشر تغييرات البرنامج والواجهة والخصائص، ولا يشمل المنيو أو المنتجات أو الريسيبي أو الأسعار أو المخزون أو الطلبات أو الموظفين أو شعار المحل. تبقى هذه البيانات والإعدادات خاصة بكل محل.
- إذا كانت إعدادات البيع عند نفاد المخزون تمنع البيع، لكن الجهاز أوفلاين، يُسمح بالبيع اعتمادًا على آخر كمية محفوظة ويُعلّم تعارض المخزون للمراجعة بعد المزامنة.

### المستخدمون والصلاحيات

- مالك كل محل يدير موظفيه وصلاحياتهم داخل محله فقط.
- أدوار جاهزة قابلة للتعديل: كاشير، مدير فرع، مسؤول مخزون، وHR.
- صلاحيات المستخدم ترتبط بالفروع والموديولات المتاحة في اشتراك المحل.
- PIN الكاشير منفصل عن كلمة مرور مالك/مدير المحل وعن كود تفعيل الكمبيوتر.

## 3. تصميم تقني مبدئي

- **القرار الحالي (2026-10-24):** بسبب حد إنشاء المشاريع المجانية وعدم توفر وسيلة تحقق إضافية، نبدأ محليًا بتصميم قاعدة Supabase واحدة متعددة العملاء بدل إنشاء حساب/مشروع جديد لكل محل. لا يُنقل أي محل إلى هذا التصميم ولا يُنشر قبل اكتمال عزل البيانات والتحقق منه.
- تبقى واجهة الدخول واحدة؛ رقم المحل يحدد tenant بعد مصادقة المستخدم، ولا يُقبل `tenant_id` يرسله المتصفح باعتباره إثبات صلاحية.
- قاعدة البيانات المشتركة تحتاج `tenant_id` وعلاقات وفهارس وسياسات RLS لكل بيانات التشغيل، مرتبطة بهوية موثقة. يلزم تحويل تسجيل دخول PIN للكاشير إلى جلسة محددة المحل قبل إلغاء وصول `anon` الحالي.
- سجل المنصة المركزي يحفظ رقم المحل وحالته وباقته وحدوده ورابط تعريف tenant والأجهزة/الرخص. يمكن أن تشترك بيانات الإدارة والتشغيل في المشروع نفسه، مع صلاحيات وجداول منفصلة.
- لا يوضع مفتاح `service_role` أو أسرار إدارة Supabase/Vercel في المتصفح أو برنامج الكاشير؛ إنشاء المستخدمين وأكواد التفعيل يتم عبر مسار خادمي موثوق.
- لوحة التحكم قد تشترك في النطاق العام مع بوابة الدخول، لكن عمليات الإدارة الحساسة تحتاج واجهة خادمية وصلاحيات موثوقة.
- تهيئة البريد مطلوبة لاستعادة كلمة المرور وتنبيهات الاشتراك.
- يجب أن يبقى نشر الواجهة منفصلًا عن بيانات كل محل؛ المنيو والمنتجات والريسيبي والأسعار والمخزون والطلبات والموظفون تظل بيانات tenant خاصة به.

## 4. فجوات ومخاطر شوهدت في النسخة الحالية

هذه ملاحظات محلية محدودة، وليست تدقيقًا لقاعدة الإنتاج:

1. `next.config.mjs` يحدد تصديرًا ثابتًا، وعميل Supabase في `src/lib/supabase/client.ts` يقرأ عنوان المشروع ومفتاحه من `NEXT_PUBLIC_SUPABASE_*` وقت البناء. لا يوجد حاليًا اختيار ديناميكي لمشروع Supabase حسب رقم المحل.
2. النموذج الحالي يحدد بيانات حسب `branch_id`؛ لا يظهر نموذج `tenant_id` أو سجل لاشتراكات ورخص العملاء.
3. `useBranchStore.ts` يحتوي قيمة افتراضية وتعليقات خاصة بفرع مدينتي.
4. `desktop/main.cjs` يثبت `PRODUCTION_ORIGIN` على موقع سانكي. لا يوجد حاليًا ربط أولي ديناميكي بجهاز/فرع/محل عبر كود تفعيل.
5. البحث المحدود لم يجد لوحة SaaS مركزية أو مسارات اشتراك/ترخيص في واجهة المحل الحالية.
6. `supabase/schema.sql` يذكر أن PIN دخول الموظف ليس جلسة Supabase Auth، وأن بعض سياسات RLS الحالية تمنح `anon full access`. هذا مانع إطلاق تجاري إلى أن تُعاد صياغة المصادقة وسياسات قاعدة البيانات وتُختبر؛ فصل قاعدة البيانات يقلل تداخل المحلات لكنه لا يحمي بيانات محل منفرد إذا بقيت سياساته مفتوحة.

## 5. خطة تنفيذ مقترحة

1. **إثبات عزل tenant محليًا:** تعريف هوية موثقة للمالك والكاشير، ربطها بالمحل والفرع، ثم سياسات RLS تمنع القراءة والكتابة خارج tenant. لا تستخدم قيمة tenant يختارها العميل من الواجهة كحد أمني.
2. **ترحيل مخطط التشغيل:** إضافة `tenant_id` للجداول التشغيلية والعلاقات والقيود والفهارس، ثم إزالة سياسات `anon full access` فقط بعد اكتمال مسارات المصادقة البديلة.
3. **تحديث API ومزامنة الكمبيوتر:** تمرير جلسة موثقة لكل القراءة والكتابة، مع الحفاظ على البيع أوفلاين ومزامنة الطلبات دون السماح بتبديل tenant على الجهاز.
4. **بناء سجل الإدارة المركزي:** ربط أرقام الحسابات والاشتراكات والحدود بهوية tenant في المشروع نفسه، وتقييد إدارة هذه السجلات لمالك المنصة.
5. **بوابة الدخول المشتركة:** رقم المحل + البريد + كلمة المرور، استعادة كلمة المرور، والتحقق من ربط الهوية بالـ tenant بعد الدخول.
6. **إنشاء محل تجريبي فارغ:** معالج إعداد وإعدادات الهوية والعملة والضريبة والإيصال، والتأكد من عدم نسخ بيانات سانكي.
7. **الفروع والباقات والرخص:** حدود الفروع والأجهزة، رسائل بلوغ الحد، إصدار الأكواد وإبطال الأجهزة ونقلها.
8. **مزايا الكاشير حسب الباقات:** تقارير الأساس، التوصيل ورسومه وأنواع الطلبات، إضافة الطاولات، ثم HR والمخزون والولاء وFinance حسب المصفوفة.
9. **اختبار قبول تجاري:** اختبار فصل البيانات بين محلين، PIN وصلاحيات، حدود الرخص، انتهاء اشتراك، انقطاع إنترنت، المخزون السالب، تغييرات الأسعار، البريد، والطباعة قبل تشغيل أول عميل فعلي.

## 6. نقاط تحتاج قرارًا قبل التنفيذ

- كيف تُولد أرقام المحلات الأربعة وتُمنع إعادة استخدامها، وهل سقف 10,000 عميل مقبول على المدى المتوقع.
- هل يختار الكاشير فرعًا جديدًا بعد تفعيل جهاز مرتبط بفرع محدد، أم يظل الفرع ثابتًا حتى تعديل الربط من لوحة المالك.
- سلوك الطلبات المخزنة محليًا عند انتهاء الاشتراك: ستُرفع عند عودة الاتصال حتى لو انتهى الاشتراك، وفق احتياج المطابقة المالية.
- سياسة الاحتفاظ بنسخة المحل الذي ألغي: مكان حفظها، مدة الاحتفاظ، وصلاحية استعادتها.
- تعريف دقيق لبيانات التشغيل التي يجب توفرها أوفلاين، وطرق دفع/خصومات/ولاء التي تتطلب تحققًا من الخادم.
- كيفية إبقاء جلسة كاشير آمنة على جهاز الكمبيوتر مع استمرار الدخول والعمل أوفلاين بعد إلغاء PIN المجهول الحالي.

## 7. حدود التنفيذ الحالية

- تحديث هذه الوثيقة يثبت اختيار قاعدة مشتركة محليًا فقط؛ لم يتغير أي منطق أو قاعدة بيانات أو إعداد نشر.
- النسخة الحية لم تُعدل ضمن هذا التوثيق.
- وضع المشروع المحلي يتضمن تغييرات وملفات غير متتبعة سابقة؛ يجب الحفاظ عليها عند بدء تنفيذ مستقل ومراجعة حالة Git أولًا.
